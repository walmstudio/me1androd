# ME1 Port (Android и Linux) — как устроен исходный код

Этот документ для тех, кто читает или правит исходники. Здесь коротко описано, как работает порт «под капотом». Подробная версия с примерами сгенерированного кода, картой памяти и разбором каждой подсистемы лежит в `docs/ARCHITECTURE.pdf` (исходник: `docs/ARCHITECTURE_full.md`).

## Идея в одном абзаце

Mass Effect (PC, 2007) — 32-битная программа для Windows/x86. Эмулятора здесь нет: машинный код игры **заранее** (статически) переводится в C, а затем компилируется обычным компилятором под ARM64 (Android, Linux aarch64) или x86-64 (Linux). Что программа ждёт от Windows (kernel32, user32, Direct3D 9, DirectInput, XInput, OpenAL и т. д.), то реализует сам порт. Это слой HLE (high-level emulation). Картинка выводится через OpenGL ES 3 или Vulkan, звук идёт через AAudio на Android или SDL2 на Linux. Данные игры (`.upk`, `.ini`, видео) берутся с диска пользователя без изменений.

```
 MassEffect.exe + DLL (x86 PE)
          │  tools/recomp.py  (capstone → C)
          ▼
 out/<mod>/code_*.c, module.c, image.bin
          │  clang/gcc  -march=armv8.2-a+rcpc
          ▼
 libme1game.so ── runtime/rt.c ……………… гостевая память, CPU, диспетчер вызовов
               ├─ runtime/hle_*.c ………… Win32 / COM / D3D9 / ввод / звук
               ├─ sm3_glsl.c + GL/VK …… шейдеры D3D9 → GLSL / SPIR-V
               └─ settings/ …………………… ini, пресеты, моды
          │  GameActivity (процесс :game)
          ▼
 Android: EGL/GLES 3 или Vulkan, AAudio, сенсор/геймпад

 Linux:   тот же код + linux/me1_linux.c (SDL2) → один файл me1-linux; X11/Wayland, Vulkan или EGL, SDL audio;
          лаунчер linux/launcher.c → me1-launcher (настройки, моды, запуск me1-linux)
```

## 1. Рекомпилятор (`tools/`)

- **`recomp.py`** разбирает PE-файл (`pefile_min.py`) и находит весь код. Отправные точки: точка входа, экспорты, указатели на код в данных (vtable, колбэки, с релокациями), `push offset`/`mov offset` в коде и дополнительные «семена» (`ilt_seeds.py`, `tools/seeds`). От них строится замыкание по вызовам. Таблицы `switch` восстанавливаются по релокациям.
- **`ehscan.py`** читает таблицы SEH (EH3/EH4) и C++ EH (FuncInfo). Так находятся обработчики `__except` и продолжения `catch`, на которые нет прямых переходов.
- Каждая функция x86 превращается в C-функцию `void m_<адрес>(CPU* c)`:
  - регистры хранятся в структуре `CPU`, флаги — в локальных переменных C;
  - переходы внутри функции — это `goto`, прямой `call` — обычный вызов C;
  - косвенные вызовы идут через `dispatch_call()`, импорты — через `call_import()`.
- **`fpsse.py`** транслирует x87, SSE/SSE2 и MMX. `LOCK`-инструкции переводятся в атомики хоста. Неподдержанное превращается в `UNIMPL()`, чтобы такие места было видно при запуске.
- **`difftest.py`** проверяет транслятор: случайные последовательности x86 выполняются в Unicorn и через recomp→C, а затем результаты сверяются (регистры, флаги, x87/XMM, память).
- **`recomp_all.sh`** перекомпилирует все модули: `m` = MassEffect.exe, `crt`/`cpp` = msvcr80/msvcp80, `dx` = d3dx9_31, `pxc`/`pxl` = PhysX, `ogg`/`vb`/`vf` = Vorbis, `bk` = Bink.

## 2. Ядро рантайма (`runtime/rt.h`, `rt.c`, `rt_fp.c`)

- **Гостевая память** — арена на 4 ГиБ (`mmap NORESERVE`). Гостевой адрес — это просто смещение в ней, поэтому указатели игры работают как есть.
- **`CPU`** хранит регистры общего назначения, `fs_base`, стек x87 (в `double`), MXCSR, XMM и MMX. У каждого потока свой `CPU`.
- **Модель памяти x86 (TSO) на ARM64.** Обращения к стеку и TEB — обычные загрузки и записи. Остальные идут через acquire/release (`LDAPR`/`STLR`). Многопоточный код игры видит тот же порядок, что и на x86.
- **Загрузчик модулей** берёт `image.bin` или исходный PE из папки игры, применяет релокации и сверяет CRC с версией, под которую собран код. Импорты связываются с экспортами других модулей или с HLE-заглушками.
- **`dispatch_call`** — переход по гостевому адресу. Адрес из области заглушек уходит в HLE. Для остальных адресов работает кэш с прямым отображением, а при промахе — двоичный поиск в таблице функций модуля.

## 3. HLE: «Windows» внутри порта (`runtime/hle_*.c`)

Импорт, который нечем закрыть гостевой DLL, получает 16-байтную заглушку в области `0xF0000000`. Вызов попадает в `hle_invoke`, тот вызывает C-реализацию, а затем снимает аргументы со стека по stdcall.

| Файл | Что реализует |
|---|---|
| `hle_win32.c`, `hle_vmem.c` | кучи, VirtualAlloc/Free и карта адресного пространства |
| `hle_sys.c`, `hle_exe.c` | модули, LoadLibrary/GetProcAddress, kernel32/user32/gdi32/advapi32 (реестр), ole32, winmm |
| `hle_thread.c` | потоки (pthread), события, мьютексы, семафоры, критические секции, TLS, распределение по ядрам |
| `hle_seh.c` | исключения SEH/C++ (RaiseException, RtlUnwind, аппаратные исключения) |
| `hle_fs.c` | виртуальная ФС: пути `C:\…` → папки Android, регистр букв, моды, подмена ini в памяти |
| `hle_mod.c` | PhoneModify: лимиты отрисовки, ключи ini, точечные патчи |
| `hle_input.c` | DirectInput8 (мышь/клавиатура) и XInput 1.3 |
| `hle_al.c` | собственный программный OpenAL 1.1 → AAudio |
| `hle_d3d9.c` + `_gl.h`/`_vk.h` | Direct3D 9 поверх GLES 3 или Vulkan |
| `hle_hb.c` | heartbeat и сэмплирующий профайлер |

## 4. Графика

- **`hle_d3d9.c`** — COM-объекты D3D9 (устройство, текстуры, буферы, шейдеры). Это маленькие гостевые объекты, их vtable состоит из HLE-заглушек. Заблокированные (Lock) данные лежат прямо в гостевой памяти.
- **HLSL.** Шейдеры UE3 компилирует настоящий компилятор из перекомпилированной `d3dx9_31.dll`. Результат кэшируется на диске, поэтому первый запуск занимает несколько минут, а следующие проходят быстро.
- **`sm3_glsl.c`** переводит байткод SM 1.x–3.0 в GLSL ES 3.00 и при необходимости эмулирует особенности чисел с плавающей точкой D3D9 (`ME1_FP_EXACT`).
- **Бэкенды:** `hle_d3d9_gl.h` (GLES 3 через EGL) и `hle_d3d9_vk.h` (свой Vulkan-рендерер; GLSL → SPIR-V через `libme1spv.so`). Есть и вариант Zink (Mesa поверх Vulkan) с пользовательскими драйверами через libadrenotools.
- **Запросы видимости** (с v1.1.3) — настоящие запросы GPU: Vulkan даёт точное число сэмплов, GLES — «видно / не видно». Раньше игра всегда получала «видно», поэтому ничего не отсекала, а блики линз светили сквозь стены. `ME1_OCCLUSION=2` — не ждать GPU, `0` — старое поведение.

## 5. Android-часть (`android/`)

- **Лаунчер** (Java, `MainActivity`): находит папку игры, показывает настройки, пресеты, драйверы GPU и раскладку управления. Затем он собирает аргументы и переменные окружения и запускает `GameActivity` в отдельном процессе `:game`.
- **`game_jni.c`** — вход в `libme1game.so`: поверхность, касания, клавиши, мышь, геймпад, вибрация и статус. Лог пишется в `Documents/me1exe_run.log`. Если драйвер GPU падает несколько раз подряд, игра завершается с кодом 77 и перезапускается.
- **`me1port_jni.c`** — мост настроек для лаунчера. Он использует тот же файловый слой, что и игра.
- **Экранное управление** (`ControlsOverlay`): стандартная раскладка (клавиши ПК или Xbox-геймпад) и с v1.1.3 раскладка «как в порте Skyrim» (A/B/X/Y, бамперы, курки, стик на всю левую половину экрана, кнопка клавиатуры телефона). Обе можно менять в редакторе.

## 5a. Linux-часть (`linux/`)

- **`me1_linux.c`** — фронтенд на SDL2, аналог `GameActivity` + `game_jni.c`. Он разбирает параметры, находит папку игры, выставляет те же переменные `ME1_*`, что и лаунчер, создаёт окно и запускает `me1_exe_main` в потоке игры со стеком 16 МиБ. Главный поток остаётся у SDL и обрабатывает события, звук и геймпады.
- **`runtime/me1_platform.h`** — общее описание окна: `Me1Window {kind, display, xwindow, surface, w, h, gen}`. Фронтенд сообщает тип платформы (`me1_platform_set`), а бэкенды по нему выбирают EGL-дисплей (`EGL_PLATFORM_X11/WAYLAND`, `wl_egl_window`) или Vulkan-поверхность (`VK_KHR_xlib_surface` / `VK_KHR_wayland_surface`). Когда меняется `gen`, пересоздаётся поверхность или swapchain. SDL при этом свой GL-контекст не создаёт.
- **Ввод:** scancode SDL → VK/DIK → `hle_ui_key`; мышь через `hle_ui_pointer_rel` (относительное движение, виртуальный курсор), `hle_ui_wheel`, `hle_ui_char`; геймпады SDL → `hle_xinput_set`, обратно вибрация. Закрытие окна идёт через `hle_ui_close` (WM_CLOSE).
- **Звук:** `hle_al_out_open/start` открывают SDL audio вместо AAudio, колбэк SDL вызывает микшер `hle_al_render()`.
- **Экран загрузки** (`me1_linux.c`): до первого `Present` окно рисует сам фронтенд (X11 — программный рендерер SDL, Wayland — GL-рендерер SDL), показывая счётчики `me1_status()`. После первого кадра окно передаётся рендереру игры через `me1gl_set_window`; на Wayland — новым окном.
- **`launcher.c`** — лаунчер `me1-launcher`, аналог `MainActivity`: immediate-mode интерфейс `ui.c` на `SDL_Renderer` (шрифты и картинки вшиты через `assets.S`), переводы `i18n.c` (словари Android + `linux/i18n`), опрос видеокарт `gpuprobe.c`. Настройки — тот же `settings/me1settings.c`, что и у `me1cfg`; игра запускается дочерним процессом `me1-linux`.
- **`demo_d3d9.c`** подменяет `me1_exe_main` небольшой сценой D3D9 и позволяет проверить окно, ввод, звук, рендереры и экран загрузки (`ME1_DEMO_LOAD`) без файлов игры (`make linux-demo`).
- На x86-64 упорядоченные обращения TSO — обычные `MOV`, на aarch64 — `LDAPR`/`STLR`, как на Android.

## 6. Настройки (`settings/`)

Файлы `Default*.ini` игры **никогда не изменяются**. Изменения пользователя хранятся в `me1port_overrides.ini` и подставляются в память, когда игра читает Default-файл. Параметры порта лежат в `me1port.ini`. Автопресет выбирает качество по GPU/SoC, объёму RAM и частоте CPU. CLI-утилита `me1cfg` делает то же из командной строки.

## 7. Запуск игры по шагам

1. `GameActivity` загружает `libme1game.so` и вызывает `nativeStart`.
2. `main_exe.c` загружает модули `crt`, `cpp`, `pxl`, `pxc` и `m` (по необходимости ещё Vorbis, Bink и D3DX) и связывает импорты.
3. Вызывается точка входа EXE: старт CRT → статические конструкторы → `WinMain`. Дальше работает код самой игры. Всё, что она просит у Windows, обслуживает HLE.

## 8. Отладка

- `ME1_HB=10` раз в 10 с пишет строку `[hb]`. В ней видно, где находится каждый поток: в каком API он заблокирован или в какой гостевой функции работает (`fn+off`).
- `ME1_PROF_HZ` — частота сэмплирующего профайлера.
- `runtime/test_*.c` и `tests/` — модульные тесты подсистем (ФС, D3D9, GL, HLSL, OpenAL, Vorbis, Bink, моды, EH, многопоточность).
- `PERF.md` — замеры производительности и куда уходит время.
